# 架构

## 分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层    mcp/（contract-mcp，MCP stdio）· HTTP /v1 · React 管理后台 │
├──────────────────────────────────────────────────────────────────────┤
│ 认证层    主密钥 ct_…（只存 SHA-256）· IP 白名单 · 每分钟限流（Redis）│
│          错误密钥过多封 IP · 套餐额度 / 透支判断                     │
├──────────────────────────────────────────────────────────────────────┤
│ 路由层    engine.ts：按优先级试服务商，5xx/429/超时/断网/坏凭证/404   │
│          → 下一家；连续失败进入冷却（Redis，多实例共享）             │
├──────────────────────────────────────────────────────────────────────┤
│ 标准化层  每个工具一种统一结构（publish_time、author…），三种输出： │
│          JSON / Markdown / 纯文本；流式为 NDJSON                     │
├──────────────────────────────────────────────────────────────────────┤
│ 服务层    providers/*.ts：7 类 15 个工具，39 个服务商（18 个不需要密钥），全部走官方    │
│          或公开 API                                                  │
├──────────────────────────────────────────────────────────────────────┤
│ 管控层    Postgres（用户、密钥、积分流水、调用记录、按天汇总、健康   │
│          日志）· BullMQ worker（健康探测、汇总、月度发放）· 后台     │
└──────────────────────────────────────────────────────────────────────┘
```

原需求里的"基础设施层"（账号池、住宅 IP 池、伪造浏览器指纹来绕过平台风控）**没有实现，以后也不会实现**：那是规避平台检测的手段，违反各平台条款。需要平台数据时，走官方 API，或者接合规的数据服务商，把它作为一个 provider 加进来。

## 一次调用的数据流

```
Agent ──MCP──▶ contract-mcp ──HTTP──▶ gateway
                                        │ 1. IP 被封？密钥有效？白名单？限流？
                                        │ 2. 余额 ≥ 工具单价？（专业版、企业版可透支到 -overage_limit）
                                        │ 3. engine.run(tool, params)
                                        │      ├─ 服务商 A ──✗ 500 ──▶ 记录失败（可能进入冷却）
                                        │      └─ 服务商 B ──✓ 一条条流出（按 dedupe 键去重）
                                        │ 4. 流式：每条写成 NDJSON 的 item 行，最后一行 done
                                        │    非流式：收齐后按 format 渲染
                                        │ 5. 同一个事务：写 usage_events，扣积分，写 credit_ledger
                                        ▼
                                     Postgres / Redis
```

## 故障转移引擎

- **顺序：** 未冷却的服务商按工具里写的优先级排在前面；正在冷却的排到最后，只在前面都失败时才试（半开）。
- **触发切换：**
  - 5xx、429、超时（两条结果之间超过 `timeoutMs`）、网络错误、401/403（我方凭证坏了）、404（这家没有，换一家）；
  - 400 直接返回给调用方，不换服务商。
- **重试：** 同一家最多重试 `retries` 次；429、401、403、404 不重试同一家。
- **冷却：** 在 `cooldownMs` 时间内失败达到 `failThreshold` 次，就进入冷却。worker 每 60 秒探测正在冷却的服务商，探测通过立刻恢复；就算没探测，冷却期满也会自动回到原来的优先级。
- **流式中途切换：**
  - 结果按"条"产生：搜索是一条结果，抓取是一段 Markdown，行情是一个报价。
  - 引擎把已经发给客户端的条目按工具的 `dedupe` 键记下来；当前服务商在流中途失败时，丢弃它，向下一家重新请求，只把没发过的条目接着发出去。
  - 客户端始终看到一条合法的流，以 `done` 结束；中间没有错误行，也不会有半截 JSON。
  - 去重键的取法：搜索、帖子、商品用 URL；抓取用段落的规范化文本；单值结果（报价、余额）用常量，所以备用服务商不会再补发一个。
- **已知限制：**
  - 备用服务商的内容可能和主服务商不完全一样（比如 direct 不执行 JS，抓到的段落更少）。拼接保证不重复、不中断，不保证逐字一致。
  - 如果主服务商在已经发出部分条目后才失败，最终结果是"主服务商的前半段 + 备用服务商的其余部分"。

## 数据表

见 `db/schema.sql`：

| 表 | 内容 |
|---|---|
| `plans` | 基础版 / 专业版 / 企业版：每月积分、能否透支、透支上限、价格 |
| `users` | 当前余额 `credits`、套餐、本期结束时间 |
| `api_keys` | 主密钥哈希、提示、每分钟限额、IP 白名单、吊销时间 |
| `credit_ledger` | 每一笔积分变动（月度发放 / 充值 / 扣费） |
| `usage_events` | 每次调用：工具、分类、实际回答的服务商、故障转移经过、是否流式、耗时、积分、IP |
| `usage_daily` | worker 每小时汇总，用于账单视图 |
| `provider_health_log` | failure / cooldown / recovered / probe_fail |

## 后台任务（BullMQ）

| 任务 | 频率 | 做什么 |
|---|---|---|
| `health-probe` | 60 秒 | 用每个服务商的 `probe` 参数试一次正在冷却的服务商，通过就恢复 |
| `usage-rollup` | 1 小时 | 把 `usage_events` 汇总进 `usage_daily` |
| `monthly-grant` | 1 小时 | 到期用户进入新一期：余额 = min(当前余额, 0) + 套餐月度积分。透支要在新一期里还上，没用完的积分作废 |

## 和原需求的差异

| 原需求 | 本实现 |
|---|---|
| 1800+ 工具、59+ 服务 | 15 个工具、39 个服务商，结构上可以随便加 |
| 社交：知乎、B站、小红书、TikTok、Instagram、LinkedIn | 没有开放搜索 API，未接；目前接了 X、Reddit、Hacker News、Bluesky、YouTube |
| 电商：亚马逊、淘宝、京东、TikTok Shop | 需要联盟或商家资质，未接；目前接了 eBay、Best Buy（官方 API） |
| 爬虫：BrightData | 它的核心卖点是绕过反爬，未接；目前接了 Firecrawl、Jina、直接抓取 |
| 账号池、住宅 IP、指纹模拟 | 不做 |
| 品牌 / 名字 | 不照搬，叫 Contract |
